# DNS 与 IPv6

适用于 iPhone / iPad

## 保持默认还是自定义

先使用默认 DNS。只有需要访问私有域名、指定解析器或解决可复现的解析问题时，再进入「设置 → DNS」调整

自定义 DNS 支持界面列出的普通 IP、DoH、DoH3、DoQ、DoT 和 TCP 地址格式；多个服务器用逗号分隔，留空恢复自动默认值。这里的自定义服务器用于隧道外解析等场景，不能简单理解为所有域名都只经这一项解析

1. 进入「设置 → DNS → 新增 DNS 规则」
2. 选择精确、后缀或通配匹配，填写你的域名
3. 根据需求选择地址、别名、分流 DNS 或 Always Real IP（始终真实 IP）
4. 保存并排列顺序，从上到下第一个匹配项生效
5. 重新发起请求，在 DNS 检查中核对解析结果

例如，把自有内网域名送到可访问的公司解析器，而不是把全部公共域名都交给内网 DNS。填写服务器前先确认当前路由能到达它

## IPv6

在「设置 → IPv6」查看相关选项。目标网络、节点与本机网络都可能影响 IPv6 可用性，出现问题时先做单项开关对照，再恢复需要的设置

模块也可能贡献 DNS 配置，解析结果不符时同时检查 [模块顺序](/oixcloud/modules)。不要同时更改 DNS、节点与规则，否则无法确定是哪一项起作用

## 示例：只把内部域名交给公司 DNS

假设你拥有 `corp.example.com`，公司解析器能从当前网络访问：

1. 添加后缀匹配 `corp.example.com`，操作选择「分流 DNS」
2. 服务器填写公司实际提供的解析器地址；图中的 `192.0.2.53` 是文档地址，不能直接使用
3. 启用并保存，将这条规则放在会覆盖它的宽泛规则之前
4. 重新请求一个真实的内部主机名，核对解析答案，再检查访问该地址所需的 VPN、路由或子网权限

DNS 解析成功只表示获得了地址，不代表已经有到该地址的路由。指定别名或地址记录也不能替代网络连接

| 现象 | 下一步 |
| --- | --- |
| 所有域名同时失败 | 检查解析器可达性和当前网络，先撤回本次变更作对照 |
| 只有内部域名失败 | 核对匹配方式、规则顺序、公司 DNS 和公司网络连接 |
| 返回地址正确但连接失败 | 检查路由、节点、IPv4 / IPv6 及目标端口 |
| 与预期规则不一致 | 检查网络预设是否覆盖全局设置，以及模块贡献的 DNS 设置 |

## DNS 泄漏：哪些设置有帮助

DNS 测试列出的是解析器，不一定是代理出口；解析器与节点国家不同，也不能单独证明泄漏。需要核对的是：本应由代理处理的域名，是否被本机交给了运营商或其他非预期解析器

当前客户端用隧道内 DNS 和 Fake-IP 接管系统查询，但直连、排除路由判断、IP / GeoIP / ASN 规则和真实 IP 例外仍可能触发隧道外解析。即使最终连接经过代理，也可能已经查询过本地 DNS；切到全局模式不能保证消除这些查询

1. 确认 oixCloud 处于已连接状态，查看目标请求的实际出口，同时检查 [网络预设](/oixcloud/networks) 和模块是否覆盖 DNS 或路由
2. 如需避免普通明文 DNS，在「设置 → DNS → 自定义 DNS 服务器」填写当前网络可访问、证书有效的 DoH / DoT 等加密解析器，例如 `https://1.1.1.1/dns-query`；保存后重新发起请求。它加密客户端到解析器这一段，**不等于通过代理发送**，解析器仍可能看到本机公网 IP
3. 检查「始终真实 IP」和分流 DNS 规则，仅保留确有需要的域名范围。域名规则有助于减少为分流而解析真实 IP 的需要，但优先级更高的排除路由等条件仍可能要求解析；不要为通过测试盲目删除局域网规则
4. 检查浏览器自带的安全 DNS、系统加密 DNS 描述文件和其他网络扩展。排查时记录原设置，暂时停用自行指定的解析器，让查询由客户端接管；若保留应用自己的 DoH / DoT，则应确认其连接也经过预期代理，端口 53 接管无法控制这类加密请求
5. 到「设置 → 高级设置」关闭「隐藏 VPN 图标」，再在「设置 → IPv6」核对 IPv6 是否实际被接管。客户端停止返回 AAAA 记录，不等于系统 IPv6 已被关闭；应同时验证 IPv4、IPv6 的出口

### 包含所有网络的作用与限制

需要加强系统流量接管时，可在「设置 → 高级设置 → 隧道」评估启用「包含所有网络」。它与「兼容性增强模式」互斥，可能影响 HomeKit、连接与重连以及应用更新；更新 oixCloud 前先断开连接

这个开关控制系统流量进入隧道，不能把客户端自身的隧道外 DNS 自动改为代理 DNS。局域网与排除路由也应单独检查，不应把它当成“零 DNS 泄漏”开关

**如果要求业务域名的 DNS 必须经代理、代理不可用时也不得退回直连，当前自定义 DNS 设置不足以保证这一点**。这需要客户端提供独立的代理 DNS 出站和失败即停止的策略，并覆盖分流预解析、真实 IP 例外及其他 DNS 查询类型；不能仅靠更换一个 DNS 地址实现

上述菜单适用于 iPhone / iPad，不代表 Apple TV 提供相同选项

## 如何验证 DNS 路径

1. 记录客户端版本、模式、节点、DNS 设置及当前 Wi-Fi / 蜂窝网络
2. 在连接前后分别运行使用随机新域名的 DNS 测试，避免缓存掩盖实际查询；将列出的解析器与自己配置的上游对照，不要求其国家或 IP 与节点完全相同
3. 在 [请求与 DNS 检查](/oixcloud/diagnostics) 中核对域名、命中规则与出口。手动 DNS 检查会主动解析域名，其结果不能单独代表普通代理连接的 DNS 路径
4. 若仍出现本地运营商解析器，分别检查分流预解析、直连规则、模块、应用自带 DNS 和 IPv6；有条件时在自己的路由器或上游网络抓包确认查询是否直出
5. Wi-Fi / 蜂窝切换、断线重连后再测。只检查 UDP / TCP 53 无法证明不存在直连 DoH / DoT / DoQ，普通连接成功也不代表通过了断线期间的保护验证

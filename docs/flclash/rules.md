打开配置操作菜单中的「覆写」

| 模式 | 行为 |
| --- | --- |
| 叠加 | 保留订阅规则与策略组，加入个人设置；个人规则优先于订阅规则，已有附加规则保持优先 |
| 自定义 | 自己维护规则与策略组，适合明确知道完整路由结构的用户 |

首次调整建议从叠加开始。自定义内容为空时不能得到一份可用路由，不要为了“清理默认规则”直接切换为空配置

## 为网站指定路线

1. 在覆写中添加个人规则，或进入「工具 → 进阶配置 → 附加规则」
2. 选择域名后缀等规则类型，填写 `example.com` 这样的匹配值
3. 选择直连、拒绝或已存在的策略组；需要 Tailscale 时选择对应网络
4. 保存并应用，保持规则模式
5. 重新发起请求，在连接记录中核对命中规则

不要把完整网页地址填进域名字段。修改规则后旧连接可能继续存在，应重新打开目标页面再判断

## 添加策略组

在覆写中创建有明确名称和有效成员的组，再引用它。重命名或删除组时检查个人规则引用，避免留下不存在的目标

## 覆写脚本

「工具 → 进阶配置 → 脚本」用于修改生成配置，不是网页 HTTP 重写脚本入口。使用可信脚本，先保存可恢复的配置，发生问题时停用脚本并对照

改动应放在长期保留的覆写入口，直接编辑下载来的订阅文件可能在下次同步时丢失

规则类型与匹配语法可参考 [mihomo 官方路由规则文档](https://wiki.metacubex.one/config/rules/)。具体目标名称以当前配置里的节点和策略组为准，不能直接照抄示例中的组名

## 叠加示例：只改一个域名的出口

先在代理页确认已有「工作」策略组，再在当前配置的叠加覆写中添加域名后缀 `example.com`，目标选择「工作」。保存并检查配置，使用规则模式访问一个测试目标

如果规则没有生效，按以下顺序检查：流量是否进入客户端、是否仍为规则模式、优先级更高的附加规则是否先匹配、组名是否存在，以及是否用旧连接验证。删除示例规则后重新应用，可恢复原订阅对此域名的处理

全局附加规则会影响不同配置，配置覆写中的个人规则只属于该配置。希望一个例外只用于一份订阅时，优先放在该配置的覆写里

## 查找进程开关与按需识别 {#process-lookup}

在「工具 → 常规 → 连接 → 查找进程」查看开关及当前说明。当前维护版本的行为如下，旧版没有相应说明时先核对版本：

| 状态 | 行为 |
| --- | --- |
| 开启查找进程 | 主动查找进程，可能增加开销 |
| 关闭，但当前规则需要进程信息 | 检查相关规则时仍按需查找，界面提示「当前规则含进程规则，仅在检查这些规则时查找进程」 |
| 关闭，且普通规则不需要进程信息 | 不为普通规则主动查找，连接记录可能没有进程名称 |

引用可能包含进程规则的 classical 规则集，也可能触发按需识别。关闭开关不等于所有进程识别都被禁止；桌面下载程序的强制直连是下面的独立策略

排查进程规则时，先确认目标程序的流量进入客户端，再保存并应用配置，用新连接核对命中规则与出口。不要仅凭进程名称为空判断规则失效；同样，其他设备经局域网代理接入时，不能假定本机能识别远端进程

## 桌面端 BT 程序直连 {#bittorrent-direct}

当前维护版本在 Windows、macOS、Linux 上，对能够识别的本机 BT 下载程序（如 qBittorrent、Transmission、Deluge、aria2c、Motrix）强制使用 `DIRECT`。该策略优先于规则和全局模式，不能通过订阅、个人规则或关闭进程查找选项取消

因此，这些已识别连接使用本机网络出口，对端可能看到本机公网 IP。不要用“全局模式已开启”判断 BT 是否经过代理；在连接记录核对进程和出口。这不是对所有 P2P 流量的协议识别保证，也不能套用到 Android 或通过局域网代理接入的其他设备

## 脚本选项与恢复

脚本选项支持手动刷新，刷新后核对尚未保存的输入，并通过预览查看新增、修改和删除。配置所引用的脚本缺失或应用失败时，先处理提示，再重新应用

从备份恢复的脚本需要检查内容后手动启用。恢复配置成功不等于脚本已开始影响路由，见 [备份与恢复](/flclash/backup)
